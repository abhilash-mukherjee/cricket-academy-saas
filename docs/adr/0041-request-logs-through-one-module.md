# Request traces go through one module, with Player and Registration fields intact

Each API request is already one trace. A command — a `lib/` function a route awaits that returns `{ ok: true }` or `{ ok: false, error }`, such as `acceptRegistration` — writes one line onto it through one module that owns the Sentry calls, at each of those returns. The route handler is not the command. The message is a plain sentence for what that return did, such as `Registration accepted successfully with ID: {registrationId}`. A failure in that function uses one sentence, `Registration was not accepted with ID: {registrationId}`, and the `error` already being returned is an attribute. When a success's own outcome is a word already in hand, such as `paused` or `settled`, the sentence says that. When a unique id of the thing named is already an argument or a local, the sentence includes it. Selecting one extra column on a query that already returns the row is allowed, for example, the new Registration id on create. A further query is not. A new command, and a new API session gate, follow these same rules. The message is not an action code, and it does not have to match the impersonation audit string. Success is info. A known failure, including `invalid-input`, is a warning. An unexpected throw is the exception already captured for that request, with no extra line. The message is kept whole. Each attribute string is cut at 200 characters, and the line is still sent.

The line carries values already in scope at that return: the ids the command was called with, and name, phone, email, or date of birth only when those locals are still in scope. No extra query, and no branch that chooses Guardian phone over Player phone or hoists a row out of a transaction just to log it. An id that points at the row is enough. User ids are not attributes of this line, even when the command was given one. Reads, page renders, the dev mailer, the auth catch-all, and route returns before a command (`unauthorized`, bad JSON, unknown slug) get no command-outcome line. The actor user id is a separate info line, message `actor`, attribute `userId`, written through the same module from `resolveOwnerContext`, `requireSuperAdminSession`, and the onboarding route as soon as a session user id exists, including when that gate then returns `forbidden`. Pages, public Registration create, and `unauthorized` have no actor line.

There is no separate branch record. Automatic HTTP body capture stays on, so a magic-link token, a raw body, and Player or Registration fields may appear on the trace. A logging failure never changes the response. The same rule covers a failed `impersonation_audit_events` insert after a write that already committed: the success response stands, and that insert failure is the request exception. There is no child span; duration stays on the request trace. An impersonation audit stays a separate record of a successful impersonated write. The route keeps the audit action strings it already has.

**Considered options:** `Sentry.logger` at each call site (rejected — the provider would leak into every command); a provider interface and adapter (rejected — one provider); the route logging after the command returns (rejected — the outcome and any fields still in scope are inside the command); masking phone and email (rejected — those fields identify the failed add or Registration when they are already in scope, and that PII on Sentry is acceptable); choosing Guardian versus Player phone, or loading a Player onto an Enrollment line (rejected — no branch and no extra read; the id is the entry point); a second query whose only purpose is a log id (rejected — an extra column on a query that already returns the row is enough); a dedicated branch recorder beside the log line (rejected — the line is the command outcome); a line at each step inside the command (rejected — the return line is what happened); a shared action vocabulary between the log message and the audit row (rejected — the sentence says what happened, and the audit string stays on the row); `actorUserId` on every command-outcome line (rejected — one early `actor` line on the trace is enough); an actor line on staff page renders (rejected — pages stay quiet); dropping an oversized line (rejected — attribute strings are cut at 200 characters so the command outcome stays whole); turning HTTP body capture off so a magic-link token and a raw body stay off the trace (rejected — a magic link on Sentry is acceptable, and the public body is useful on the same trace); a second log sink or a sampling change (rejected — one trace per request is enough at this usage); `log.error` on a known outcome (rejected — that outcome is a warning, and an unexpected failure is already the exception); a failed audit insert turning a committed write into a 500 (rejected — the client already got the success that committed).
